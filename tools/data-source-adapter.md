# 如何新增一个数据源

> 这份文档的用途：**让下一个人在不读任何工具代码的前提下，接一个新数据源进来。**
>
> 判断标准很简单——如果接一个新源需要改 `tools/` 以外的任何文件，说明架构坏了。

---

## 1、为什么要有适配器层

气象数据的现实是：**没有两个源的格式是一样的。**

| | 打包 | 分隔符 | 编码 | 要素名 | 单位 | 缺测码 | 质控 | 站号 |
|---|---|---|---|---|---|---|---|---|
| DWD CDC 日值 | 每站一个 `.zip` | 分号 | latin-1 | `TXK` / `RSK` | °C / mm | `-999` | `QN_4` 数字等级 | 5 位 |
| GHCN-Daily | 每站一个 `.csv.gz` | 逗号 | UTF-8 | `TMAX` / `PRCP` | 0.1 °C / 0.1 mm | 空字段 | 字符标志 | 11 位 |
| 格点产品 | NetCDF / GeoTIFF | — | — | 自定义 | 自定义 | `_FillValue` | 无 | 无（需插值） |

**如果工具直接读这些格式，每接一个源就要改六个工具。** 适配器层就是为了消除这件事。

---

## 2、适配器要做三件事

```
fetch(station_ids, years)  →  原始文件（负责下载、缓存、重试、校验）
parse(raw)                 →  统一契约的日表（负责单位换算、缺测码、质控标志）
describe()                 →  元信息（提供方、URL、版本、许可、要素可用性）
```

只有 `parse` 的输出会进入下游。**原始格式到 `parse` 为止，不再向外泄露。**

---

## 3、统一契约（这是唯一的接口）

适配器必须输出这些字段，一个不多一个不少：

| 字段 | 类型 | 说明 |
|---|---|---|
| `station_id` | string | 站点标识，全局唯一 |
| `date` | string | `YYYY-MM-DD`，**当地日历日** |
| `year` `month` `day` | int | 拆分字段 |
| `doy` | int | 年内第几天，1–366 |
| `tmax_c` | float / 空 | 日最高气温，**摄氏度** |
| `tmin_c` | float / 空 | 日最低气温，**摄氏度** |
| `prcp_mm` | float / 空 | 日降水总量，**毫米** |
| `qc_flag` | string | 上游质控等级或标志；无则空 |
| `interpolated` | bool | `true` = 该值由插补得到 |
| `complete_core` | bool | `true` = `tmax_c` 与 `prcp_mm` 当日都有 |
| `source` | string | 源标识，如 `dwd-opendata` |
| `source_version` | string | 版本或获取时间，用于追溯 |

### 两条硬规则

**规则 1：空值必须是空，不能是哨兵值。**
`-999`、`-9999`、`NaN` 都不允许出现在契约里。`parse` 阶段就要转成空。

**规则 2：单位必须在 `parse` 里换算完。**
契约里的 `tmax_c` 永远是摄氏度，`prcp_mm` 永远是毫米。
上游用 0.1 °C、华氏度、英寸，都在 `parse` 里处理掉。

> **这条规则不是形式主义。** 上游单位陷阱极多：同一种产品用 0.1 单位，
> 另一种产品用十进制；同一家的不同要素可能不同。单位错一位，
> 阈值判据会整体失效，而且**数据本身看起来仍然"合理"**，极难发现。
> 因此适配器必须有一道物理量级检查（见第 5 节）。

## 4、接入步骤

### 第 1 步：写适配器

在 `tools/` 下新建 `adapters/<source_name>.py`，实现三个函数：

```python
SOURCE = "my-source"
SOURCE_VERSION = "..."          # 版本号或获取时间，写进每条记录

def fetch(station_ids, years, cache_dir):
    """下载并缓存原始文件，返回 {station_id: local_path}。"""
    ...

def parse(raw_path):
    """把原始文件解析成 {date: {...}}，字段名与契约一致。"""
    ...

def describe():
    """返回元信息字典：provider / base_url / login_required /
       elements / units / license / citation。"""
    ...
```

### 第 2 步：确认站点清单

站点清单**不写进适配器**，写进 `manifest.json`：

```json
{
  "stations": [
    { "station_id": "...", "name": "...", "lat": 0.0, "lon": 0.0, "elev_m": 0,
      "raw_file": "...", "raw_sha256": "..." }
  ]
}
```

**站点选取应当是规则化的，不是手挑的。** 推荐把规则本身写进 manifest：

```json
"station_selection_rule": "落在区域内，且 2000–2024 年核心要素完整度 >= 98%"
```

这样站点集合可复现，而不是"当时觉得这几个站不错"。

### 第 3 步：写进 manifest

```json
{
  "adapter": "my-source",
  "regions": [
    { "id": "...", "role": "primary", "box": {...},
      "period": { "baseline": [2000, 2012], "test": [2020, 2025] } }
  ],
  "upstream": { "provider": "...", "login_required": false, "dataset_version": "..." }
}
```

### 第 4 步：跑质量检查

新源必须通过与本项目相同的检查。见 `de_integrity.py`，至少覆盖：

- `tmax >= tmin` 是否**恒成立**（这是最强的单一校验，能抓住大部分解析错误）
- `tmin <= tavg <= tmax`（如有日均值）
- 极值是否落在物理可能范围内
- 给定日期范围的实际完整度（**不要相信库存声明的年份范围**）

> **库存元数据会说谎。** 一个源可能在索引里声明"覆盖 2000–2024"，
> 实际中间有若干年几乎是空的。**完整度必须逐日实测**，不能读声明。

### 第 5 步：重新标定判据

**绝对下限必须按新区域重新标定。** 分位数部分是自适应的，可以直接沿用；
但"多少度算热浪、多少毫米算暴雨"是气候相关的，换个气候区就不成立。

标定方法见 `de_criteria.py`：扫描候选下限，选择使**基线期本身**产出
约 0.3–1.5 次/站/年的值。判定标准是「既不把常态当极端，也不让判据空转」。

## 5、必须有的三道防线

接一个新源时，下面三件事**任何一件不做都会在后期付出代价**。

### 防线 1：物理量级检查

解析完先问一句：「这个数字可能是真的吗？」

真实案例：某源的温度字段是 0.1 °C，误当整度读取后，
全年最高温变成 3.9 °C、年降水变成 100 mm——
**数字本身不报错，代码也不崩，但整个数据集已经废了。**

所以 `parse` 之后必须打印量级摘要并与常识对照：

```
tmax 最高/最低、tmin 最低、年降水总量范围、湿日占比
```

年降水量在温带应该是 300–1500 mm 量级。如果算出 100 mm，就是单位错了。

### 防线 2：逐日完整度实测

按站、按年、按要素统计实际天数，**不要读元数据声明**。
把结果写进 manifest 的 `per_year_core`，让下游能看到逐年的真实覆盖。

### 防线 3：已知事件复现

挑几个**有公开记录的历史极端事件**，检查判据能否检出。

这是唯一能证明「判据不是空转」的方法。如果连 2012 年欧洲寒潮都检不出，
说明下限定错了——此时不要调松到「能检出」为止，要先确认数据本身对不对。

---

## 6、换源之后怎么确认结论稳定

数据源换了，结论可能变。**变不是问题，说不清为什么变才是问题。**

做一次对照实验，比较新旧两个源在**同一条工具链**上的输出：

| 情况 | 含义 | 处理 |
|---|---|---|
| 事件表完全一致 | 结论与源无关，最理想 | 直接采用 |
| 差异可归因（如新源补上了旧源缺失的日期） | **正常且有益** | 记录差异来源 |
| 差异无法解释 | 有解析或单位错误 | 回到防线 1 排查 |

**判据不是"结果必须相同"，而是"差异必须可解释"。**

---

## 7、常见陷阱清单

- [ ] 上游单位是 0.1 度还是整度？（**同一个提供方的不同产品可能不一样**）
- [ ] 缺测码是什么？`-999`、`-9999`、空字符串、还是 `NaN`？
- [ ] 日期是**当地日**还是 UTC？跨时区会让"当日最高温"错位。
- [ ] 文件编码是 UTF-8 还是 latin-1？中文/德文站名会暴露这个。
- [ ] 站号在不同源之间**不通用**，不要在工具里做跨源站号匹配。
- [ ] 库存声明的年份范围 ≠ 实际完整度，必须逐日实测。
- [ ] 许可是否允许再分发？影响能不能把数据放进提交物。
- [ ] 是否有 `sha256` 可校验？没有的话至少记录获取时间。
